## 剪贴板自动巡访（新增功能）

需求：复制到 8 位数字 UID 就自动触发面板上「手动巡访」那条链路，但复制过的 UID 不再触发。

实现：
- 新增 `clipboard_monitor.py` / `ClipboardUIDMonitor`
  - Win32 ctypes 轮询，**先看 `GetClipboardSequenceNumber()` 判变化**，变了才 OpenClipboard（避免每 0.4s 抢剪贴板锁跟输入法/截图工具打架）
  - 读文本必须 `wstring_at(ptr)` 读到 NUL 为止；**不能** `wstring_at(ptr, 4096)`，会越过 GlobalAlloc 块尾读出整片垃圾（已踩坑）
  - `extract_uid()`：纯 8 位数字直接命中；≤40 字短文本里恰好 1 个 8 位数字才猜（兼容 `UID:10813721`）；长文本/多候选一律不猜
  - 三层去重：①自身 seen 集合（落盘 `clipboard_seen.json`，最近 2000 条，重启仍生效）②`task_handler.is_processed()`（任何通道跑过的都不再触发）③同 UID 还在 pending/running 不重复入队
  - 启动基线：服务启动时把当前剪贴板序号当基线，旧内容不自动跑，只打日志提示"重新复制一次即可触发"
- `task_handler.py`：`submit_manual(..., source="手动")` 增加来源参数；新增 `is_processed()`；手动/剪贴板提交增加「同 UID 在队列中」防重
- `server.py`：`_on_clipboard_uid` 回调（回调返回值 queued/skipped/error 决定是否记「复制过」，error 不记 → 可重试）；`/api/clipboard/{status,start,stop,config,clear}`；startup 启动监听、shutdown 停止；`/api/status` 带 clipboard
- `index.html`：手动巡访卡片加「监听剪贴板」勾选 + 状态行（目标/已触发/跳过/最近 UID）+「清空剪贴板记录」；实例下拉变更自动同步给后端；WS 新增 `clipboard` 消息类型（自动触发时面板提示）；任务来源新增「剪贴板」标签（`.src-cb`）

验证：extract_uid 11 个边界用例全过；模拟复制 → 首次入队、重复复制跳过、新 UID 再触发；隔离起 8011 实例做真实 HTTP 测试通过（未干扰用户正在跑的 8000 服务和模拟器）。
注意：用户当时 8000 端口跑着老代码，需重启服务生效。

## 服务启动方式（重要）
- **agent 后台启动的服务会随会话结束被回收**（实测：20:55 起 74 分钟后被杀，21:xx 起 5 分钟后被杀，事件日志无 python 崩溃记录）
- 长期挂机用项目根目录 `启动服务.bat`（双击，独立窗口、自动开浏览器）／`停止服务.bat`（按端口杀进程）
- 从 agent 侧启动时用 detached+breakaway 才不会被回收：
  `subprocess.Popen([...server.py], creationflags=0x00000008|0x01000000, stdout=open('server_detached.log','ab'), stdin=DEVNULL)`
- 日志文件：`server_detached.log`

## 坏 UID 卡 30s 修复（empty_list 模板）

用户反馈：粘贴错误 UID 一直"等待中"。原因链：
1. 主号通道串行，一个任务卡住后面全排队（显示等待中是正常的，问题是单个坏 UID 太慢）
2. 游戏**改版**：无效 UID 不再推荐一堆玩家（旧的 count_player_cards>=2 判定失效），
   而是停在找朋友页给「可能认识的玩家 + 暂时没有内容(幽灵图)」空列表
3. 状态机认不出 → 干等 12s 搜索超时 → 盲点头像 3 次 → ~30s/个

修复：从 debug_caps/visit_fail_20261020_221207.png 裁了幽灵+文字区域做 `empty_list` 模板
（exe 基准 235x196，box [176,682,411,878]，阈值 0.85；正样本 0.979，负样本最高 0.44）。
`_wait_search_result` 里搜索 3s 后命中且连续两帧(≥0.4s)确认 → not_found，坏 UID 从 30s 降到 ~4s。
教训：裁模板时 x 坐标别忘了也按 1033/1920 换算（第一版把 1092 宽当 1920 算，正样本得分 -0.03）。
建议加进 spec 后要在真实截图上跑正负样本再上线。

另外发现：suggest_title.png 文件丢了（git 显示 deleted），「可能认识的玩家」标题模板实际不可用。

⚠️ 遗留：instance_1 游戏被踢下线（「已在另一台设备登录」，点重启也没用），需要用户处理账号；
empty_list 修复只做了离线验证，还没在真机跑通。

## 真机验证 empty_list 修复 + ADB 重连加固（10-21 凌晨）

用户重启游戏后实测：
1. 第一次报「MuMu 后台截图分辨率读取失败」→ 游戏重启使服务进程的长连接 IPC 会话作废，
   `/api/discover` 重建引擎解决（旧连接 close + 新建）。
2. 接着报「adb device offline」→ 引擎重连只做 `adb connect` 救不回 offline 状态，
   手动 `disconnect` + `connect` 恢复。
3. 修复验证通过：无效 UID 10813723 → not_found，**6 秒**完成（此前 30s+）。

加固（下次重启服务生效）：
- `visit_engine._adb_device`：重连前先 `adb disconnect`
- `adb_controller.ADBInstance.connect()`：get-state 发现已 offline 时先 disconnect 再 connect，
  且 connect 后再 get-state 确认（connect 成功≠状态正常，这次 /api/adb/connect 假报 True 的根源）

教训：MuMu IPC 长连接和 ADB 连接在游戏/模拟器重启后都会失效，引擎里要有自动重建；
服务重启后模拟器端游戏会话也可能被顶，任务失败先截图看游戏状态再查代码。
